## I6 — gokbase Live Voice (Gemini Live): real-time voice lift map

Read-only internal route, 2026-10-08. Scope per D-006: lift gokbase's production "Live Voice" pilot (`backend/app/rag/live/*`, the voice WebSocket, cost ledger, and the frontend widget) into the Arena's real-time spoken-interview feature. Owner's stated conflict (D-006/BRIEF.md line 11): gokbase's live model is pinned to the Gemini Developer API (`vertexai=False`, API key), not Vertex — directly contradicting D-001 ("Gemini via Vertex only"). This route maps the full stack and isolates exactly what depends on the AI-Studio key, answering what is provider-agnostic vs. bound.

### 0. What this is, precisely

gokbase's Live Voice is a **public-profile** feature: a visitor on a candidate's public profile page opens a real-time spoken Q&A session with an AI voice assistant that answers questions about that one candidate from their knowledge base (RAG-grounded), using Gemini Live (`gemini-3.1-flash-live-preview`). It is NOT an interview-subject role-play and NOT an investigator-coaching tool — it is single-agent (one voice assistant, one visitor), single-direction retrieval (search a KB, answer), with no adversarial role, no deception, no scenario engine, and no multi-party turn structure. The Arena's use case (spoken interrogation of a role-playing subject, SOL-1 "text is the scored artifact") is architecturally similar at the transport/session layer but functionally different at the "what does this session DO with the model" layer. This matters for the lift-map: the session/transport/safety/cost-metering/persistence layers lift closely; the retrieval-tool and prompt layers are domain-specific to gokbase's KB-Q&A use case and need a near-total rewrite for interview role-play + evidence-release + deception.

### 1. Architecture (high confidence)

**Not** a provider-abstracted ephemeral-token architecture. It is a **1:1 server-side WebSocket proxy**: `FastAPI WS <-> LiveVoiceSession (backend) <-> genai.Client.aio.live.connect() <-> Gemini Live`. The browser never holds a provider credential — it holds only a short-lived, single-use, server-minted ticket (then a rotating server-issued resume token). This is the opposite of a client-side-ephemeral-token pattern; the server owns the entire Gemini session lifecycle.

Flow (first connect):
1. Browser `POST /public/profile/{handle}/voice/ticket` (authed, `Depends(get_current_user)`) → server runs a full eligibility gate (profile published, `voice_enabled`, `is_voice_pilot` allowlist, platform `LIVE_VOICE_ENABLED` kill-switch), fail-closed quota check, mints a single-use Redis ticket (`voice_ticket:{token}`, TTL 90s) binding `{asker_user_id, owner_user_id, handle, ip_hash}`. Source: `/Users/balla/Desktop/satvik/gokbase-org/backend/app/api/api_v1/endpoints/voice.py:311-400`.
2. Browser opens `new WebSocket(wsUrl, [ticket])` — the ticket rides as the WS **subprotocol**, never the URL (no query-string credential leak). Source: `.../frontend/src/sections/knowledge-base/public/voice/useVoiceSession.ts:60-72,436-473`.
3. Server WS route (`voice.py:596-900`): validates Origin in the handshake (pre-ticket-consumption), echoes the subprotocol (avoids a silent 1006), `getdel`s the ticket (atomic single-use), re-runs the FULL eligibility gate post-consumption (state may have changed between mint and connect), `INSERT`s the `voice_sessions` row **before** opening the Gemini socket (crash-safe FK), then constructs `LiveVoiceSession` and calls `.run()`.
4. `LiveVoiceSession.run()` (`session.py:2470-2515`) opens `client.aio.live.connect(model=..., config=...)`, starts two concurrent tasks — `receive_loop()` (Gemini→browser) and `safety_loop()` (2s tick: duration/idle/cost) — alongside the main coroutine's own `_pump_client_audio()` (browser→Gemini, driven by `ws.receive()`).

Reconnect/resume uses a **separate subprotocol marker** (`["voice-resume", token]`), server-side credential rotation (GETDEL, single-use), and Gemini's native `session_resumption` handle (stored server-side in the Redis credential, never the browser) — a transient drop is resumable up to 3 attempts; the browser's resume logic lives in `useVoiceSession.ts:406-431` (backoff 500/1000/2000ms).

### 2. Audio formats, sample rates (high confidence)

- **Capture (browser→Gemini):** 16 kHz, mono, Int16 PCM LE, via a dedicated `AudioContext({sampleRate: 16000})` + AudioWorklet (`capture-processor.js`, a same-origin static asset, not inline/blob) posting ~250ms chunks; relayed as raw WS binary frames. `_INPUT_MIME = "audio/pcm;rate=16000"` constant in `session.py:80`. Source: `.../frontend/.../audioController.ts:8-13,29,169-215`.
- **Playback (Gemini→browser):** 24 kHz, Int16 PCM LE from Gemini, converted to Float32 and pushed into a ring buffer inside a second dedicated `AudioContext({sampleRate: 24000})` + `playback-processor.js` worklet. Web Audio forbids mixing sample rates in one graph — hence **two separate AudioContexts**, a real constraint worth lifting verbatim. Source: `audioController.ts:9-13,92-112,217-232`.
- Connect config pins `response_modalities=["AUDIO"]` only (never `["TEXT"]` — TEXT trips a 1011 error per the code's own documented finding) and both input/output audio transcription ON (`types.AudioTranscriptionConfig()`), which is how the text transcript is derived (the Arena's SOL-1 requirement that voice stays presentation-only and text is the scored artifact maps directly onto this — gokbase already produces a parallel text transcript stream via `output_transcription`/`input_transcription` events, never relies on audio alone). Source: `session.py:1368-1395`.

### 3. VAD and barge-in (high confidence)

Server-side VAD only — `realtime_input_config.automatic_activity_detection(silence_duration_ms=700)` (constant `_VAD_SILENCE_MS = 700`, `session.py:81,1380-1384`); no client-side VAD. Barge-in is Gemini-native: when the model detects the visitor speaking over it, the Live API emits `server_content.interrupted=True`; gokbase relays this as a visitor-facing `{"type":"interrupted"}` frame (`session.py:1913-1915`) and the frontend's `AudioController.flush()` instantly clears the playback ring buffer (`audioController.ts:234-240`); the state machine returns to `listening` (`voiceMachine.ts:210-213`). This barge-in handling is fully provider-generic in its WS/UI half (any "the model got interrupted" signal would route the same way) but the *detection* itself is Gemini Live's own VAD feature, configured via the connect config.

### 4. Input/output transcription (high confidence)

Both directions transcribed by the Live API itself (`input_audio_transcription` / `output_audio_transcription` config flags), never a separate ASR call. Each transcript fragment is persisted as its own `transcript_in`/`transcript_out` event row (NOT batched per full turn — `session.py:1895-1912`) and relayed to the visitor as `{"type":"transcription", role, text}`. A documented, load-bearing quirk (`audit.py:22-32`): **one spoken answer = many contiguous `transcript_out` fragment rows** (the model streams text token-by-token); a "turn" must be reconstructed downstream as the maximal contiguous run between boundaries (`transcript_in` / `tool_call` / `tool_response`). Any Arena code that scores "the subject's answer" per turn must implement this same reconstruction — it is not optional, the data literally arrives fragmented.

### 5. Tool calling during live sessions (high confidence)

Tools are declared via `types.FunctionDeclaration` / `types.Tool` at connect time (`session.py:569-768`) — six tools in gokbase's KB-Q&A use case (`search_sections`, `get_section`, `gather_evidence`, `skills_table`, `career_timeline`, `suggest_kb_source`), none of them Arena-relevant by name, but the **dispatch mechanics** are fully reusable: tenant/identity is server-injected and never model-controllable (`user_id` stripped from model args, `session.py:1526-1529`); duplicate tool-call ids while a response is pending are suppressed, cancelled ids are discarded and never responded to (`session.py:1716-1843`); the Live API requires the response `id` to be echoed back or the response is **silently dropped** (a documented P0 trap, `session.py:17-18`); batched function calls in one `tool_call` message run concurrently via `asyncio.gather` over `asyncio.to_thread` (sync DB calls off the event loop) but respond in original incoming order, never timing order. All model-supplied tool args are sanitized (`_sanitize_inbound_args`, prompt-injection defense reused from `app.rag.v3.injection_defense` — zero-width/bidi/forged-tag stripping) before execution or any log/DB write — directly relevant to the Arena's deceptive-subject threat model (SUB-7: "must not... attack the actual platform"; prompt-injection attempts invalidate a session).

### 6. Session caps (high confidence)

Config constants (`/Users/balla/Desktop/satvik/gokbase-org/backend/app/core/config.py:553-577`):
- `LIVE_VOICE_MAX_SESSION_SECONDS = 480` (8 min hard duration cap, close code 1000)
- `LIVE_VOICE_IDLE_TIMEOUT_SECONDS = 90` (no audio either direction → close 4408)
- `LIVE_VOICE_MAX_COST_USD_PER_SESSION = 0.50` (hard per-session USD cap → close 4413)
- `LIVE_VOICE_PER_PROFILE_DAILY_SESSIONS = 50`, `LIVE_VOICE_PER_PROFILE_DAILY_SPEND = 5.0`, `LIVE_VOICE_PLATFORM_DAILY_SPEND = 50.0` (day-bucketed quotas, Redis, fail-closed on the pre-mint gate, best-effort/fail-safe on the mid-session spend write)
- `LIVE_VOICE_TICKET_TTL_SECONDS = 90`

Enforcement is a 2-second `safety_loop` tick (`session.py:2203-2241`) checking duration, idle, and `_cost_kill_check_effective()` — the cost check is **cross-leg**: `max(local in-memory meter, a shared Redis `voice_spend:<session_id>` counter)`, closing a known abuse vector where a client opens a second concurrent "resume" leg to double the effective budget (`session.py:2178-2201`). This per-session-cap-survives-reconnect design (with carried-cost baked into every resume credential, `session.py:1221-1226,2285-2297`) is directly reusable for the Arena's per-trial/per-candidate cost ceiling inside the $100 bake-off cap (D-007).

### 7. Ticketing and auth (high confidence)

Two-stage: (1) an authed JWT-gated mint producing a single-use, short-TTL Redis ticket server-side (never a provider credential, never a long-lived token in the browser); (2) the WS handshake validates Origin (against a profile-subdomain allowlist) **before** consuming anything, echoes the requested subprotocol (avoiding a known Chrome/websocket 1006 failure mode on subprotocol mismatch), and atomically `getdel`s the ticket. A full eligibility re-check runs at BOTH mint time and WS-connect time (state — e.g., an owner toggling a flag — can change in the gap) — `voice.py:271-308`. This whole ticket-mint-then-WS-subprotocol pattern is provider-agnostic and a strong lift candidate for the Arena's judge-facing hosted demo (D-008: judges must not be able to exhaust the $100 cap).

### 8. Cost metering (high confidence)

`LiveCostMeter` (`session.py:315-487`) consumes each Live API `usage_metadata` frame and accumulates **billed tokens per modality** (audio-in/out, text-in/out) — explicitly never diffing cumulative counters (a documented bug class: a counter can drop between frames) and never deriving cost from wall-clock audio seconds (a documented "COST-DRIFT" rider — Live audio bills at a fixed 25 tokens/second-equivalent, not measured seconds). Pricing is DB-loaded per modality-suffixed `model_pricing` rows (`gemini-3.1-flash-live-preview:audio` at $3.00/$12.00 per 1M in/out, `:text` at $0.75/$4.50 per 1M — migration `179_voice_ledger_layer_fix.sql:62-72`, dated 2026-07ish; **flag: >12 months-fast-moving pricing should be re-verified against current Vertex Live rate cards before reuse, per the BRIEF's staleness rule**). An honesty state machine (`meter_status`: verified / degraded_no_frames / degraded_no_modality) ensures the system never silently under-reports cost confidence — a pattern directly reusable for the Arena's EVL-5 cost/latency disclosure requirement.

### 9. Persistence / ledger tables (high confidence)

Two tables (migration `180_voice_sessions.sql`):
- **`voice_sessions`**: one row per session, INSERT-before-connect, single rollup UPDATE on disconnect (`end_cause` taxonomy: `NULL`=in-flight/crashed-resumable, `'suspended'`=transient-drop-resumable, anything else=terminal), RLS owner-read + service-role-write-all.
- **`voice_session_events`**: seq-ordered, single-writer, append-only per-turn transcript+tool ledger (`UNIQUE(session_id, seq)` total order, closed `kind` enum: `transcript_in/out, tool_call, tool_response, tool_cancelled, interrupted, session_meta`), **written per-fragment, not batched at session end** — a crash loses nothing already written. This crash-loss-zero, append-only event-log design is a strong structural match for the Arena's SCN-10 requirement ("every change is versioned and timestamped... append-only trial event log") and directly reusable for the interview transcript ledger regardless of voice at all.
- Migration `179_voice_ledger_layer_fix.sql` widens a shared `rag_v11_cost_ledger` CHECK constraint to add a `'voice_session'` layer value — this is gokbase-specific legacy-table coupling, not reusable as-is (the Arena has no `rag_v11_cost_ledger`), but the pattern (a regression test that parses the migration file and cross-checks the layer-name list, `test_cost_ledger_layers.py`) is a good practice to copy.
- Migrations `181_public_profiles_voice_pet.sql` / `182_voice_pet_styles.sql` (not read this route — flagged open question) are almost certainly the companion-pet wiring already covered by I5's gokbase/cloudforce delta report; not re-profiled here to avoid duplication.

### 10. Safety loop (high confidence)

The 2-second `safety_loop` tick is the single enforcement point for duration/idle/cost, each with a **distinct WS close code** (`1000` normal, `4408` idle, `4413` cost, plus `4401` auth / `4403` origin / `4404` not-found / `4503` resume-failed) so the client can distinguish retry-worthy vs. terminal drops. A documented race-safety invariant: `_terminal_close_initiated` is set as the very first statement in `close()`, before any socket operation, specifically so a concurrent disconnect-observer task cannot misclassify a deliberate kill (cost/duration/idle) as a resumable "suspend" (`session.py:1330-1341,2736-2765` — "a kill can never become a resumable suspend" is called out explicitly as a security-adjacent invariant, "resumption-as-bypass... forbids"). This pattern — a hard kill switch that cannot be raced into a soft-resume — is directly relevant to the Arena's SCN-10/BKO safety requirements around session integrity.

Separately, a platform-wide `LIVE_VOICE_ENABLED` kill-switch is checked both at ticket mint AND on every mid-session safety tick (`session.py:2217-2221`) — an owner can kill every live session instantly, which maps to the Arena's $100 hard-stop requirement (D-007).

### 11. Injection defense / prompt-injection framing (high confidence, directly Arena-relevant)

Every tool payload returned to the model is run through `app.rag.v3.injection_defense.sanitize_untrusted_text` + `wrap_evidence(..., salt)` with **one per-session unguessable salt** minted at session construction (`session.py:1279-1285`), so the system prompt can draw a DATA-vs-INSTRUCTIONS boundary the model is told to respect, and a forged "close tag" injected via owner KB content or ASR-transcribed visitor speech cannot break out of the salted region. Model-supplied tool args are sanitized **before** execution and before any log/DB write (spoken injection via ASR into tool args is explicitly called out as an attack surface, `session.py:830-876`). This is the single most directly reusable security pattern for the Arena's deceptive-subject threat model: a deceptive subject's "sealed per-turn disclosure tag" (REQUIREMENTS.md ambiguity #5) and a scenario's hidden evaluator-only packet (SCN-9) both need exactly this kind of salted DATA/INSTRUCTION boundary so a subject-candidate LLM cannot be social-engineered into leaking its hidden role/facts through a crafted investigator question routed through a tool call.

### 12. Error handling and reconnection (high confidence)

A documented end-cause taxonomy with exactly two resumable states (`NULL`=crash, `'suspended'`=transient drop with a live Redis resume credential) and everything else terminal. Reconnection re-validates: full eligibility gate again (owner/pilot/platform flags may have changed), day-bucketed cap re-check (read-only, no re-reservation), a **hard per-session cost backstop re-check before any socket reopens** (closes a tick-granularity budget-leak where a resume could buy one extra safety-tick's worth of spend), and a null-handle guard (a resume whose stored Gemini handle is missing is refused rather than silently starting a fresh, mislabeled-as-resumed context). `receive_loop()` treats the Gemini SDK's transient iterator errors as retryable up to 3 consecutive failures before declaring the Gemini-side transport dead and marking the session suspended (`session.py:1847-1882`). This whole reconnection contract is provider-generic in its WS/Redis/DB half; only the specific **Gemini `session_resumption` handle** (`types.SessionResumptionConfig`, `new_handle` read from `session_resumption_update` frames) is Gemini-Live-API-specific — Vertex's Live API would need the equivalent resumption primitive verified (see §14).

### 13. Tests (high confidence — file inventory, contents sampled not exhaustively read)

`backend/tests/rag/live/` (24 test files) covers: cost-kill end-to-end (`test_cost_kill.py` — feeds real usage frames through `_consume`, proves the full frames→meter→cost→close(4413)→credential-delete→resume-rejected chain, and the race-safety "kill wins over suspend" invariant), cost meter unit tests, cost ledger layer-CHECK/migration cross-check, quota spend + quotas, concurrent-resume cap (the overlap-leg exploit), reconnect-widen, deterministic tools, get_section ownership preflight, search tiers, TOC builder, prompt contract (the compliance-probe harness importing the SAME `build_system_prompt` production uses), owner channel (cost-never-reaches-visitor), audit judge + rolling mean + writer, voice-frames-security (the artifact-frame primitive/allowlist/byte-cap gauntlet), injection-defense wiring, scoped retrieval, gather_evidence. `backend/tests/api/test_voice_ws.py` covers the WS route itself: subprotocol echo, ticket replay rejection (4401), expired/unknown ticket (4401), INSERT-before-connect row carries the right asker, resume with mismatched asker rejected (4503), cap-kill closes with the mapped code AND invalidates the resume token, and the full Origin matrix (foreign origin → 4403 with the ticket surviving unconsumed; missing origin → 4403; valid subdomain origin proceeds) — using a fake in-memory Redis double and a patched `LiveVoiceSession.run` so the Gemini API itself is never hit in tests. This test suite's shape (fakes for Redis + WS + a patched session.run, asserting close codes and DB-patch contents) is a directly reusable test-harness pattern for the Arena's own voice-session tests.

### 14. Which parts are provider-agnostic vs. AI-Studio-bound (the core D-006 question)

**Bound to the Gemini Developer API (AI Studio), load-bearing, documented in the code itself:**
- `session.py:1397-1408` — `_client()` constructs `genai.Client(api_key=settings.GEMINI_LIVE_API_KEY, vertexai=False)` with `vertexai=False` called out as **explicit and load-bearing**: "the backend process env carries Vertex vars... for the main RAG pipeline, which flip the SDK into Vertex mode — and the Vertex Live endpoint rejects API keys (1008 'API keys are not supported by this API'). Live Voice is PINNED to the Gemini Developer API (SPEC D2 — the live model is Gemini-API-only)." This is the one hard-conflict line with D-001.
- `settings.GEMINI_LIVE_API_KEY` — a distinct, API-Studio-only secret, documented as reading from local `.env` in dev and destined for Secret Manager at deploy (`config.py:557-561`). Confirms the project's own engineers knew this key is a second, parallel credential path outside the Vertex ADC flow the rest of the stack uses.
- `settings.LIVE_VOICE_MODEL = "gemini-3.1-flash-live-preview"` — an AI-Studio model id string; Vertex Live model ids/availability were NOT independently re-verified in this route (see open questions).
- The pricing rows in migration `179` are keyed to this exact model id string with a `:audio`/`:text` suffix convention — if the Arena points at a different Vertex Live model id, the pricing keys, not just the client, must change.

**Provider-agnostic (the overwhelming majority of the engineering, by line count and by design intent):**
- The entire WS transport/ticket/mint/Origin/subprotocol-echo layer (`voice.py`), the entire quota/day-bucket system (`quotas.py`), the entire cost-metering SHAPE (per-modality token accumulation, honesty states — only the rate-card numbers and the modality-key strings are model-specific), the entire persistence/ledger layer (`events.py`, migrations 180), the entire safety-loop/close-code/end-cause taxonomy, the injection-defense salted-wrapper pattern, the entire frontend (WS client, state machine, audio worklets, reconnection/backoff) — **none of this imports `genai` directly except `session.py`**, and `session.py` itself isolates the provider call to exactly two points: `_client()` (the constructor) and `_build_config()` / the tool-declaration + `types.*` surface (which is the `google-genai` SDK's typed config objects — these exist in both the AI-Studio and Vertex code paths of the same SDK, so the TYPES likely do not need to change, only the client construction and the model id).

**What would change to point at a Vertex Live model (concrete, scoped):**
1. `_client()`: `genai.Client(vertexai=True, project=..., location=...)` using ADC (ambient service-account credentials, matching the rest of the stack) instead of `api_key=...`. Likely the SINGLE highest-leverage code change if Vertex Live is available for the project/region.
2. `settings.LIVE_VOICE_MODEL`: swap to the correct Vertex Live model id/path (Vertex model ids and resource-path conventions sometimes differ from AI-Studio model ids — not independently verified here).
3. `settings.GEMINI_LIVE_API_KEY` removed/retired; the env-var "Vertex mode auto-flips the SDK" behavior that gokbase's comment says it must explicitly opt OUT of (`vertexai=False`) would instead need to be the DEFAULT (consistent with the rest of a Vertex-only Arena stack) — this removes a whole secret-management surface (API key rotation, Secret Manager entry) in exchange for ADC, which also better matches D-003's platform constraints.
4. Pricing-table rows in a `179`-equivalent migration must use whatever Vertex's modality-specific Live rate card actually is (not necessarily identical dollar figures to the AI-Studio-era card seeded here, and the `179` migration's rates are gokbase-specific, dated mid-2026 — must be re-verified, not assumed, flagged below).
5. `types.LiveConnectConfig` kwargs (response_modalities, audio transcription config, VAD silence_duration_ms, voice config, session_resumption) are `google-genai` SDK types — whether Vertex's Live endpoint supports the identical kwarg set (especially `session_resumption`, `realtime_input_config.automatic_activity_detection`, and the prebuilt-voice/`language_code` combo) is **not verified in this read-only route** — this is the most important open technical question before assuming a drop-in swap (see open questions).
6. Everything in §9-§13 (persistence, cost ledger shape, safety loop, tests, frontend) needs **zero change** for a Vertex swap — they interact with `LiveVoiceSession` as a black box, not with the `genai.Client` directly.
