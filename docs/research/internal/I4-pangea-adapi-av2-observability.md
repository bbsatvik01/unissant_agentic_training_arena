## 1. How assistant v2 is built

**Framework**: Google Agent Development Kit (ADK) 2.2.0, `google-adk[db]==2.2.0`, a single `LlmAgent` per turn (`/Users/balla/PangeaChat/adapi-av2/app/assistant/agent.py:49-114`). Agent is rebuilt per request — cheap, stateless about scope by design (agent.py:1-29).

**Model provider**: Gemini via Vertex AI (matches the Unissant arena's own locked constraint, REQ R7/owner constraint). `GOOGLE_GENAI_USE_VERTEXAI=true` + `GOOGLE_CLOUD_PROJECT` + `GOOGLE_CLOUD_LOCATION` set in process env (confirmed live in both task definitions: staging `pangea-chat-admin-dash`/`us-central1`, prod `pangea-chat-prod-admin-dash`/`us-central1` — `task_definition_staging.json:77-79`, `task_definition_production.json:48-50`); AI Studio (`GOOGLE_API_KEY`) is a documented fallback path, not used in deployed envs. Default model `gemini-2.5-flash-lite`, explicitly passed (never library default) because ADK's default changed across versions (agent.py:52-58). A planned successor `gemini-3.1-flash-lite` requires moving the Vertex location to `global` (`assistant.instructions.md:45`).

**Tools**: 11 flat-schema function tools — 6 read-only analytics tools (list courses, class summary, student detail, vocab/grammar explorers, course locations), `generate_report`, `generate_lesson_plan`, `show_class_chart`, plus two conversation-content tools (`list_course_activities`, `query_activity_sessions`) (`assistant.instructions.md:31-39`). Tool schemas are **flat by hard CI-enforced invariant** — no nested Pydantic/dict argument — because ADK's `$ref`/`$defs` nested schema makes `gemini-2.5-flash-lite` emit malformed function calls (`assistant.instructions.md:41-43`). `generate_content_config.tool_config.function_calling_config.mode=VALIDATED` is a second defense layer (agent.py:86-101).

**Prompts**: `instruction` is an ADK `InstructionProvider` **callable**, not a static string — resolved fresh every turn so "today's date (UTC)" and server-injected scope never go stale (agent.py:103-107) — a concrete fix for date-hallucination bugs worth copying.

**Security model**: scope (course/portfolio) and the Matrix bearer token are never in model-visible agent state. The token lives only in a process-local, per-request `REGISTRY` keyed by an opaque `runtime_id` that *is* in session state; `before_tool_callback=enforce_tool_security` strips any model-supplied token/scope but deliberately keeps `course_id` as a legitimate portfolio-scope argument, re-verified per call (agent.py:38-42, 103-114; `assistant.instructions.md:21-29`).

**Streaming**: `app/assistant/service.py` (`stream_assistant_reply`, 2068 lines total, read lines 1-1251) orchestrates one ADK `Runner.run_async` call in SSE streaming mode (`RunConfig(streaming_mode=StreamingMode.SSE, max_llm_calls=40)`), normalizing ADK events into typed `AssistantEvent`s (`token`, `tool`, `done`, `error`, `cap_exceeded`, `canvasOpen`, `canvasError`, `chart`) for the HTTP SSE wire (service.py:285-363). Includes: a single automatic empty-turn retry, 429/RESOURCE_EXHAUSTED backoff (1s/2s/4s, capped at 3 retries, only before anything user-visible was emitted) (service.py:143-169), a numeric-grounding gate (`app/assistant/grounding.py`, reused by both the live path and the eval harness) that refuses to let a fabricated figure reach the teacher (service.py:184-190, 515-548), and a server-authored (never model-authored) success narration for report/lesson-plan/chart tools so hallucinated prose can't override resolved facts (service.py:574-690).

**Memory/sessions**: durable, multi-turn — `DatabaseSessionService` (Postgres) in deployed envs, ADK in-memory service locally/tests, no sqlite fallback (service.py:193-224). Sessions are keyed by teacher mxid + client-supplied `conversation_id`; the per-request `runtime_id` + scope are re-applied each turn via the runner's native `state_delta` rather than a separate event, so resume never leaks a stale runtime_id (service.py:1087-1119, module docstring 1-29). On the Cloud Run "assistant" role (no DB access), a `BffSessionService` proxies session reads/writes back to the BFF over HTTP carrying the teacher's bearer (service.py:263-282).

**Isolation**: the agent is intentionally stateless about *which* course it serves; the hard guarantee is the tools' per-call re-verify plus `before_tool_callback`, not the agent object (agent.py:25-28, 60-65).

Confidence: high — all direct code reads, dated by file content (OBSERVABILITY-SPEC.md references, 2026-06/07/08/09 deploy notes).

## 2. Exactly how Phoenix is wired

**Exporter / endpoint**: OTLP-HTTP (`opentelemetry-exporter-otlp-proto-http==1.41.1`) to a **self-hosted** Phoenix (`docker-compose.observability.yml:1-49`, pinned `arizephoenix/phoenix:20.8.0`, verified current 2026-09-05 per its own comment). Controlled entirely by `settings.PHOENIX_OTLP_ENDPOINT`; when unset (the default local/test state) `install_assistant_tracing` returns `None` and `get_turn_tracer()` falls back to a no-op tracer from the process-global provider — zero overhead when off (`otel_tracing.py:217-277`).

**Auth**: Phoenix container runs with `PHOENIX_ENABLE_AUTH=true` and a required `PHOENIX_SECRET` (compose errors if unset, never hardcoded); the app side sends `Authorization: Bearer <PHOENIX_API_KEY>` only when `PHOENIX_API_KEY` is set (`otel_tracing.py:245-246`). Ports bound to `127.0.0.1` only (compose:26-28) because the trace store holds teacher content + redacted-but-still-sensitive analytics.

**Instrumentor**: `openinference-instrumentation-google-adk==0.1.25` (`GoogleADKInstrumentor().instrument(tracer_provider=provider)`), the **only** span path — ADK's own native OTel tracer is deliberately left on the process-global no-op provider so there is never a duplicate span set or a double cost roll-up (`otel_tracing.py:12-18, 256-258`).

**Span kinds / structure**: ONE OpenTelemetry **parent span per turn** (`assistant.turn`, created from this provider's own tracer, not OpenInference's) made the current OTel context around the whole turn — including the empty-turn retry and the 429 backoff — so every OpenInference-instrumented ADK child span for every attempt nests under a single per-turn trace (`otel_tracing.py:15-18`; `service.py:422-456,1075-1086`). OpenInference itself supplies the LLM/tool child spans via ADK instrumentation (not hand-built in this codebase).

**Attributes on the per-turn parent span** (`service.py:435-512`): `pangea.turn.id`, `pangea.teacher_mxid` (the session id/user id for Phoenix grouping), `pangea.conversation_id`, `pangea.scope_mode`, `pangea.model`, `pangea.course_id` (if set); at turn end: `pangea.turn.cost_usd` (string, Decimal-derived, never float — "money is a string"), `pangea.turn.prompt_tokens`, `pangea.turn.output_tokens`, `pangea.turn.reasoning_tokens` (thinking tokens, billed at output rate), `pangea.turn.total_tokens`, and `pangea.turn.thinking` (the model's thought-summary text, clipped to 8000 chars, redacted, never shown to the client).

**Session and user ids**: `pangea.conversation_id` = session grouping key; `pangea.teacher_mxid` = user id, explicitly exempted from mxid-redaction (`_MXID_PRESERVE_KEYS`, `otel_tracing.py:60`) because it is the trace's own subject, not third-party PII — this is the one deliberate exception to the otherwise-blanket redaction.

**Redaction** (mandatory, runs via a custom `SpanProcessor` added to the provider *ahead of* the exporter's `BatchSpanProcessor`, so it runs under the default `SynchronousMultiSpanProcessor` before export — `otel_tracing.py:123-201,250-255`):
- Matrix access tokens (`syt_...` regex), `Bearer <token>` headers (full-token match via "to next delimiter" rather than a char-class allowlist — a documented bugfix), and JSON-serialized credential-named fields (`access_token`, `refresh_token`, `authorization`, `api_key`, `secret`, `password`, `session_key`, `cookie`, `token`) are masked on **every** exported string value, including the trusted dimensions (defense in depth) — `otel_tracing.py:75-98`.
- mxid/email redaction runs on every value *except* the preserved teacher-mxid key.
- Phoenix's own cost-driving `llm.token_count.*` attributes are **renamed** to `pangea.observed.token_count.*` before export, specifically to disable Phoenix's built-in token×price cost engine — the codebase treats the RDS `llm_traces.total_cost_usd` number (computed once by `compute_cost_usd`, stamped identically onto both RDS and the span) as the sole cost source of truth, by construction identical in both places (`otel_tracing.py:20-25,62-69,146-193`). Non-numeric values smuggled into a count attribute are redacted before the rename rather than exported verbatim — fail-closed on cost.
- Separately, `app/assistant/observability.py` holds the PII redaction used for the RDS trace `messages` array (not spans): mxid/email regexes, a `_PII_KEYS` dict-key denylist (displayname, email, mxid, user_id, tokens, secrets...), and a contextual bare-`name` rule that masks a student's name only when sibling keys (`studentId`/`mxid`/`user_id`) mark the dict as "about a student" — so course/construct titles that also use a bare `name` key are not over-redacted (`observability.py:80-152`). A 20,000-char clip guards against a pathological tool result bloating a trace row.

**Sampling**: none implemented — every turn that runs with tracing on produces exactly one parent span; no head/tail sampling config was found. Confidence: medium (absence of a sampling knob across all read files, not exhaustively grepped for a config elsewhere).

**Local vs hosted Phoenix**: explicitly **local-only** today. `docker-compose.observability.yml:1-6` states this file is "for LOCAL E2E only — never a deploy artifact" and that moving to Pangea's own hosted infra means dropping the SQLite volume for `PHOENIX_SQL_DATABASE_URL=postgresql://…` with *no code change*. **Neither `task_definition_staging.json` nor `task_definition_production.json` sets `PHOENIX_OTLP_ENDPOINT` or `PHOENIX_API_KEY`** (confirmed by full read of both files' `environment`/`secrets` blocks) — so as currently deployed, staging and prod run with tracing **off** (no-op tracer), and Phoenix only runs for a developer's local E2E session. This is a load-bearing gap for the arena if "maximum Phoenix coverage" (owner constraint) is read as "in the deployed environment."

Confidence: high on code mechanics (direct reads); high on the staging/prod gap (confirmed by full task-definition reads, not inference).

## 5. Lessons in deploy-notes about observability

`deploy-notes/2026-06-29-observability-rds.md` (full read) and `2026-06-30-observability-suite-merge-window.md` (full read) describe the **prior, now-superseded** external-HTTP-sink observability design (before the RDS-native `llm_traces` table, which itself predates the Phoenix work in `otel_tracing.py`'s module docstring, which calls itself "Phase-0 observability" distinct from this RDS work). Key lessons transferable to the arena:
- Cost truth should have exactly one source of record; this repo's answer is "RDS is the SoT, Phoenix's own pricer is disabled" — directly reusable for an arena that also needs an authoritative per-turn/per-session cost ledger separate from whatever Phoenix displays.
- Two independent spend guardrails is the pattern: a soft, non-atomic, fail-open deployment-wide monthly cap (simple SUM query) plus a per-request atomic reservation cap owned by the one process with DB access — reused because the "assistant" role here has literally no DB engine (Cloud Run, stateless) and must proxy cap/trace writes back to the BFF.
- `create_all(checkfirst=True)` bootstrap under a Postgres advisory lock avoids a multi-worker boot race creating duplicate schema objects; **future schema changes are not auto-applied** and must ship as explicit guarded migrations — a real lesson for Supabase migration discipline in the arena.
- A coordinated multi-PR merge-order note (`#22` before `#23`) because both touch the same `ensure_schema` function — a pattern (document cross-PR sequencing explicitly when two PRs touch the same migration surface) worth adopting if the arena's handoff discipline needs similar cross-PR deploy notes.
- No deploy-note specifically documents a Phoenix *outage* or production incident — the Phoenix wiring itself reads as fresh/unexercised in production (consistent with the "local-only" finding in §2).

## Implications for the arena build

- The per-turn parent-span pattern (one OTel span per logical unit of work, opened before the first model call and kept as the current context across retries/backoff, so every retry nests under one trace) maps cleanly onto the arena's "coaching within 3s for 95% of turns" (KPI-4) and "all trials: ... latency and cost" (EVL-5) requirements — a `pangea.turn.*`-style attribute set (turn id, role/session id, scope, model, cost_usd, token counts) is a close template for an `arena.turn.*` set (case id, role=assistant/subject/scorer, model, cost_usd, latency_ms).
- The "RDS/Supabase is the sole cost-of-record, rename Phoenix's own cost-driving token attributes so its auto-cost engine never diverges" pattern directly solves the arena's EVL-5/EVL-10 requirement to "publish ... cost and latency alongside rank" from one authoritative number.
- The redaction-before-export `SpanProcessor` ordering (redactor added to the provider ahead of the exporter's `BatchSpanProcessor`) is a reusable mechanism for the arena's own redaction need: scoring keys, role labels, and hidden evaluator-packet content (SCN-5, SCN-9) must never leak into Phoenix spans the same way Matrix tokens/student PII must not here — this is a directly adaptable control point, not just a convention.
- The golden-dataset + shared-checker eval pattern (same deterministic checker used live and in CI, foils included to prove the checker itself works) is architecturally close to what AST-7/EVL-8 need: a transcript-citation/evidence checker that both gates a flag's validity live and is proven against deliberately-fabricated foils in CI.
- The "assistant role has no DB, proxies cap + trace writes back to the BFF role" split is a direct precedent for the arena's own scale-to-zero, simple-architecture GCP requirement if the scorer/engine ever needs to be a separate stateless Cloud Run service from the Supabase-writing core.
- The explicit local-only Phoenix gap is a warning, not a template: do not assume "we wired OpenInference + ADK" means "Phoenix is live in the hosted judge demo" without separately provisioning and wiring a reachable Phoenix endpoint and setting the corresponding env in the actual deploy config.
- The non-strict mypy configuration and the "not yet run" live eval are both signs that even the team's own best reference implementation has known, acknowledged gaps relative to its own global CI standards (per I7) — worth weighing when deciding how much of this pattern to lift verbatim vs. tighten at adoption.
