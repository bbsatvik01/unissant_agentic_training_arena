### 3. Recurring critique themes (checklist, from critique rounds 1-7)

TechnoMile's build was **RED through round 7** (1 blocker, 3 majors unresolved as of the last audited round), with findings per round: R1 4/19/2, R2 1/15/3, R3 0/11/1, R4 2/8/0, R5 0/5/1, R6 0/3/1 (YELLOW), R7 1/3/0 (back to RED, unreviewed). The *shape* of what kept recurring is a transferable checklist for any agentic build with money, durability or security surface:

- [ ] **Fail-closed, not fail-open, on every ledger/ownership check.** Round 5-6 found repeated "ownership failures never surface, they're silently absorbed" bugs (DBOS recording a step's exception as its outcome instead of raising; a pending reservation vanishing from the aggregate allowance check at C502). For the Arena: any scoring/coaching pipeline component that can silently swallow an error (a missing turn citation, an un-raised exception in the scenario engine) must be checked explicitly, not assumed caught.
- [ ] **Lock-ordering and deadlock cycles under concurrency** (C603: admission locks taken in an order that could deadlock) — less relevant at 1-2 concurrent users, but worth a one-line sanity check if the Arena ever serializes writes to a shared run-state row.
- [ ] **No durable path for "late correction" flows** (C702: a Challenge that overturns an accepted claim had no recompute workflow) — maps to the Arena's SCN-10 (dynamic evidence release, predeclared context changes) and the Challenge rules around re-scoring after new evidence drops; make sure the scenario engine's evidence-release and re-evaluation path is actually durable/resumable, not just designed on paper.
- [ ] **Undefined numerical methods presented as if measured** (C703: no defined Pwin calculation before the deadline) — directly relevant to EVL-7's investigator rubric and EVL-9/10's formulas: make sure every score (confidence, FPR, PPV) is computed by an explicit, versioned formula, never "the model's best guess," before it ever reaches a leaderboard.
- [ ] **Dependency cycles in deliverable packages** (C704: two export work-packages depended on each other) — a process-management lesson: sequence the brief/transcript export and the scoring pipeline so neither blocks on the other's unfinished output.
- [ ] **"Closed" vs. "measured."** The owner brief itself flags: "nothing is measured... every closure is a document fix checked against local Python models... no live G0, verifier-policy result, or fresh acceptance set has run." This is the most important meta-lesson: a design document saying a gate is fixed is not the same as having run it. For the Arena, the false-positive gate (≤5%), isolation/leakage test, and the 3-second coaching-latency KPI must be measured against a running system, not just asserted in a design doc, before any bake-off ranking is trusted.
- [ ] **No-rigging discipline carried through every round**: "owner no-rigging rule," never set a CI threshold above/below its measured baseline, never claim "never pays twice" when in-flight calls can repeat, never quote a stale/non-representative baseline as if it were a true random baseline. This matches the user's own hard global rule against softening gates — the TechnoMile corpus independently re-derived the identical principle under its own critique process.
- [ ] **Scale-to-zero discipline needs an automated audit, not a promise**: `scripts/audit_cloud_run_cost.sh` exits 1 on any `min≥1`, `--no-cpu-throttling`, stray tagged revision, or missing `max-instances`, and runs in the pre-push hook. Build the Arena's equivalent from day one, since the originating incident (described in the user's own global rules) was a tagged test revision that leaked ~$415/month for ~2 months.
