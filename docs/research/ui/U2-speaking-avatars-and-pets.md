**Net read for Q1:** the industry is visibly **diverging on form**, not converging on one pattern. The two biggest players (OpenAI, Microsoft) are each pulling a dedicated full-screen/floating character *back* toward either an inline chat experience (OpenAI) or a narrower feature surface (Microsoft, Mico → tutoring only) — both moved *away* from "always-on floating character for every voice interaction" within about a year of shipping it. This is a real signal for the arena: a floating mascot-for-everything is the pattern two vendors are backing away from; a scoped, task-bound character (Duolingo's Lily, bound specifically to the video-call feature; Microsoft's Mico, now bound specifically to tutoring) is the pattern that is holding up.

## 2. Speaking-animation techniques for the browser — compared

### 2.1 Amplitude-driven motion (Web Audio `AnalyserNode`)
Unchanged from X5's finding and reconfirmed: cheapest, needs no phoneme/viseme data, works with any TTS output including Gemini TTS (which X5 confirmed returns no timing data on any tier). Feed a single continuous "mouth openness"/"talk" float from `AnalyserNode.getByteFrequencyData()` into whatever rig is chosen. gokbase's `--kin-talk` CSS-variable technique (I7, already surveyed) is exactly this pattern, already proven at 60fps-safe cost (set once per frame outside React render).

### 2.2 Viseme lip sync from text or phonemes
Confirmed again this route: the production path (Duolingo) is TTS audio -> in-house ASR for phoneme timing -> phoneme-to-viseme mapping -> Rive state machine inputs. A cheaper variant (we hold the ground-truth script text already, per X5) is text-driven viseme mapping with no ASR round-trip. **New this route:** `met4citizen/TalkingHead`'s own streaming API makes this a solved problem for a three.js-rigged avatar — `streamStart(opt)` takes a `lipsyncType` option of `visemes` (default), `blendshapes`, or `words`, and a `lipsyncLang` for word-based viseme generation; `streamAudio()` feeds live audio chunks and the class handles lip-sync playback timing itself, including an option (`waitForAudioChunks: false`) to play lip-sync without waiting on audio. [Context7 `/met4citizen/talkinghead`, `README.md`/`examples/azure-audio-streaming.html`, fetched 2026-10-08 via `npx ctx7@latest`] — H, primary repo docs, resolves X5's open question (X5 only reached mirrors, not the canonical repo).

### 2.3 Audio-reactive orbs/blobs (voice-mode-orb style)
No single named "orb SDK" exists; every product that does this (ChatGPT's retiring orb, Copilot's Mico, Gemini's older Live UI) built it in-house on amplitude/frequency data driving a shader or vector shape. For a web app, the realistic building blocks are: `AnalyserNode` for the signal, plus either a Rive `.riv` numeric view-model property, a dotLottie numeric state-machine input, or raw canvas/SVG, to render it. No vendor-specific orb primitive was found to lift.

### 2.4 Rive — data binding and audio-reactive state machines
X5 already found that Rive's legacy "State Machine Inputs" API is deprecated in favor of **Data Binding**. This route fetched the hooks directly: `useViewModel(rive, {name})` resolves a named view model; `useViewModelInstance(viewModel, {rive, useNew?, name?})` resolves/binds an instance (with `autoBind: false` on `useRive` for manual control, exactly as X5 found); `useViewModelInstanceNumber`/`...Boolean`/`...String`/`...Color`/`...Trigger`/`...Enum`/`...Image`/`...Font`/`...List`/`...Artboard` are typed property hooks built on a shared base (`useViewModelInstanceProperty`) that subscribes/unsubscribes via `prop.on(handleChange)`/`prop.off`. [Context7 `/rive-app/rive-react`, `_autodocs/api-reference/useViewModelInstance*.md`, fetched 2026-10-08] — H, primary SDK docs. Practically: an amplitude float would bind to a numeric view-model property (e.g., `mouthOpen`) set every animation frame from outside React (same technique as gokbase's `--kin-talk`, just through Rive's binding instead of a raw CSS var); a boolean `isTalking`/`isThinking` would bind similarly. Rive's own docs and third-party guides (DEV Community, "Don't Build Just Another Chatbot — Architecting a Duolingo-style AI Companion with Rive", 2026) describe the identical TTS -> phoneme -> viseme -> state-machine-input pipeline as a now-documented, repeatable pattern, not a one-off Duolingo trick. [DEV Community, https://dev.to/uianimation/dont-build-just-another-chatbot-architecting-a-duolingo-style-ai-companion-with-rive-49g5, 2026] — M, community tutorial, not vendor-primary, but consistent with the primary Rive/Duolingo sources already cited in X5 and here.

### 2.5 Lottie / dotLottie interactivity
**New this route, confirmed via Context7 primary docs.** dotLottie's state-machine format (`.lottie`) supports `Numeric`, `Boolean`, `String`, and `Event` inputs, set via `stateMachineSetNumericInput(name, value)` / `stateMachineSetBooleanInput` / `stateMachineSetStringInput`, with `stateMachineFireEvent(name)` to trigger event-guarded transitions; a `PlaybackState` entry action (`SetFrame`) can bind straight to a numeric input value (`"$cursorFrame"` in the fetched example), which is exactly the shape needed for audio-amplitude-to-frame binding (set `talkLevel` every animation frame the same way the documented examples set `scrollProgress` on scroll or `cursorFrame` on mouse move). [Context7 `/lottiefiles/dotlottie-web`, `wiki/State-Machines`, fetched 2026-10-08] — H, primary docs. 2026 roadmap additions (LottieFiles blog): **Motion Tokens**, letting animation properties (position, color, opacity, scale) bind to live data sources at runtime, and continued **Theming**/**Data Binding** work in Lottie Creator. [LottieFiles, "The Lottie Power Stack 2026", https://lottiefiles.com/blog/inside-lottiefiles/the-lottie-power-stack-2026, 2026] — M, vendor blog (promotional but primary); no example of audio-specific reactivity was found in docs — it would need to be hand-wired the same way scroll/cursor examples are, there is no built-in "audio input" binding type as of this fetch.

### 2.6 Live2D Cubism Web
No new primary-source update found this route beyond X5's existing citation; X5's open question ("verify current 2026 version/license") is **not resolved** here — out of scope budget for this pass, flagged again below. What *is* new: Live2D is the dominant rig format for the live "desktop AI companion pet" open-source genre surveyed in section 1 (Open-LLM-VTuber, AI Vpet), which is independent corroboration that Live2D remains the default choice specifically for a *companion-pet-style* character (expressive 2D, anime-adjacent), as opposed to three-vrm's niche (3D humanoid, VRM format).

### 2.8 met4citizen/TalkingHead
**X5's open question resolved: the canonical repo was reached this route (not just mirrors).** MIT license, confirmed via direct fetch — commercial use is explicitly permitted for the TalkingHead *class itself*. **Important nuance:** the README's example avatars (Ready Player Me, Avaturn) are licensed "free for non-commercial use **only**" — that restriction is on the *sample 3D model assets*, not on the TalkingHead code; a commercial deployment needs either its own licensed/custom-made GLB avatar or a Ready Player Me/Avaturn commercial tier. Fetched directly from Google's own docs (GDK), not secondary coverage:

- **What it is:** a Gemini Live API response modality (`"response_modalities": ["VIDEO"]` plus an `avatar_config.avatar_name`) that returns synchronized real-time video of a talking avatar alongside audio, over the same bidirectional WebSocket (`BidiGenerateContent`) the arena's voice plan (direction doc section 9) already targets for `gemini-3.8-live`. Supporting web coverage independently confirms Live Avatar is "generally available **in Gemini Enterprise**" with **custom avatars gated behind an enterprise allowlist/sales process**; **preset/stock avatars are available to all Gemini Enterprise customers immediately**. ## 3. Design rules for friendly, clean, premium characters (not uncanny, not childish) that stay role-independent

Extending, not repeating, X5 section 5's research-literature grounding for PRB-4 (demeanor bias can invert relative to truth) and I7's Tamagotchi/Duo cautionary findings (retention mechanics vs. aesthetic borrow). New this route:

- **Stylized/abstract beats photorealistic for avoiding the uncanny valley, and this is now the dominant 2026 industry pattern, not just a theoretical rule.** Every character surveyed in section 1 that is *not* a literal talking-head video avatar is deliberately non-human in form: Mico is a blob/flame with no body; Lily is a stylized 2D illustration, not a photorealistic render; the desktop-pet genre runs almost entirely on anime-stylized Live2D, not 3D-realistic rigs. "Opting for a non-human appearance sidesteps the risks of entering the uncanny valley... openly strange can in some ways make it more accessible." [selfielabstudio.com, "Imperfect by Design: 2026 AI Character Trends", https://selfielabstudio.com/blog/imperfect-by-design-2026-ai-character-trends-20260216, 2026-02] — M, design-blog commentary, directionally consistent with the Mico/Lily primary evidence above, not independently verified beyond that consistency.
- **Personality can be carried by voice and text alone, with zero visual form, and still be a shipped, accepted product.** Siri and Alexa are the standing counter-example to "a character needs a face"; Claude's own current no-avatar, ElevenLabs-voiced design (section 1) is a live 2026 instance of the same choice. This directly supports an option where the **coach companion** gets a visual form but the **subject avatar** does not (or vice versa) without that being an inconsistency — it is a legitimate, precedented design choice per surface, not a gap.
- **Premium reads as restraint, not richness.** Replika's own 2026 rebuild *removed* customization options (clothes, makeup, eye color) rather than adding them — a vendor with years of avatar-customization data chose to simplify. Combined with Mico's and Lily's single-silhouette (no limbs/no complex body) designs, the pattern across three independent, differently-motivated vendors in 2026 is the same: **fewer, better-animated states beat more customization surface.** This argues for the arena spending animation budget on a small number of named poses/states done well (idle, listening, thinking, speaking, flagging, evidence-released — the exact vocabulary I7 already extracted from gokbase's `fsm.ts`) rather than a large wardrobe/customization system.
- **Demeanor independent of role (PRB-4), reframed as a build rule rather than a research citation (X5 already supplied the research):** because every subject persona in the arena must use the *same* avatar rig regardless of whether that persona is playing the deceptive or truthful role in a given trial (the role is a property of the *scenario*, not the *character*), the practical rule is: **the avatar's idle/neutral baseline animation must be identical across every role assignment of the same persona, and every pose/state transition must be driven only by turn-structure events** (subject is composing an answer, subject is speaking, evidence was just released, coach is flagging something) **— never by a sentiment/confidence/stress signal derived from the dialogue content.** This is mechanically enforceable the same way gokbase's `fsm.ts` already enforces it (I7): the FSM's inputs are literally `status` (a voice/turn-state enum) and UI chrome flags (reduced-motion, mobile, dragging) — nothing in that input shape reads dialogue sentiment, and the arena's port of it should keep that same invariant by construction, not by convention.
- **The coach pet's reactions, specifically, must react to reasoning quality, not outcome or session frequency** (I7's existing finding, restated here only because it directly intersects with "stunning/alive" per the owner's brief): an "alive-feeling" pet is achievable entirely through idle-loop variety (Lily's 64-combination idle system is the concrete existence proof that this, by itself, is what makes a character "feel alive," independent of any guilt/streak mechanic) — the owner's "amazing, stunning, alive" requirement and PRB-4's "never manipulative" requirement are not actually in tension; Lily is the evidence that idle-animation richness, not engagement-mechanic richness, is what produces "feels alive."

## 6. Contradictions / disputed points (new this route)
