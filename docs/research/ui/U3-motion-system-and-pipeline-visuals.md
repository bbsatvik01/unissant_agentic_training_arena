## 1. React animation libraries, October 2026

| Library | Current version (how verified) | Bundle cost | React 19 fit | Reduced-motion handling | Best for |

**Which pairings top product teams use (option, not a pick):** the recurring 2026 pattern cited across sources is **Motion for React-state-driven UI (enter/exit, shared-element) + GSAP for anything that needs a real timeline (ScrollTrigger-driven narrative, SplitText reveals) + plain CSS transitions/`transform`/`opacity` for everything that's just hover/press feedback.** Design-reference teams named repeatedly for "quiet, premium" motion (Stripe, Linear, Vercel) are described as leaning on exactly this split rather than one single library for everything; Linear's own motion is characterized as mostly 80-120ms linear transitions with "no decoration-animations" at all — i.e. the most-copied reference in the industry uses *less* animation, not more, which is a genuine tension against "amazing, stunning animations" that the eventual design pass should resolve deliberately, not by default. TechnoMile's own precedent (`motion.md`, `web/package.json`) is the extreme version of this: **zero animation libraries**, pure CSS `transform`/`opacity` keyframes, each with exactly one assigned meaning, and it still measured 60fps (p95 16.8ms) on both a streaming dashboard and a 4x animated replay. That is a proof point that "amazing and smooth" does not require a heavy runtime — it requires discipline. **Trade-off to carry into the design pass:** a library (Motion/GSAP) buys faster iteration and built-in reduced-motion ergonomics; TechnoMile's library-free approach buys the smallest possible bundle and the most control, at the cost of hand-rolling every easing/stagger/interruption rule.

## 2. Animated pipeline / agent-activity visuals

**This product already has a measured, working internal precedent for exactly this problem** — not a hypothetical to design from scratch. Three things exist today, read in full or in relevant part this route:

1. **TechnoMile's agent-office** (`web/src/components/war-room/agent-office.tsx`, model `lib/war-room/office.ts`): every visual movement is traced to one recorded server event (`STEP_STARTED`/`STEP_FINISHED`/`ACTIVITY_SNAPSHOT`), folded into a seq-ordered, duplicate-safe schedule, replayed either live (3.5s behind the ledger to absorb clock skew) or at 8x in a finished-run replay. **Measured**, not claimed: 477-481 frames in 8 seconds, p50/p95 16.7/16.8ms, zero frames over 50ms, on both the streaming dashboard and the animated office. I7 already mapped this onto arena turn-states (`investigator-typing`, `subject-thinking`, `coach-flagging`, `evidence-released`, `finding-committed`) as the single strongest architectural fit for "agents visibly doing work" — this route does not re-derive that, it confirms the fit still holds and adds the external pattern names below for comparison.
2. **TechnoMile's pipeline view** (`docs/design/pipeline-view/SPEC.md`, read in full this route — not covered by I7): a **rail + canvas** layout — a sticky left rail lists every pipeline step grouped into collapsible phases (status glyph, elapsed time, one count, spend), a right canvas shows the *selected* step's own primary visual (source wall, verdict stream, heatmap, etc.) plus an analyst-facing one-line question per step ("What is each agent finding, and from where?"). Auto-follow tracks the live step by default; clicking a row pins it and turns follow off; gates (human-approval points) render as unanimated diamond rows so they read as structurally different from running work. This is a **named, working answer to "how do leaders show multi-agent work without clutter"**: it is progressive disclosure by construction — one step's detail is on screen at a time, the rest is a status strip, and "Open in Dossiers" links push deep detail out of the canvas entirely rather than stacking it in.
3. **TechnoMile's own motion doctrine** governs both of the above (see section 3).

**External patterns, for comparison against the internal precedent (not a replacement for it):**

- **xyflow / React Flow (`@xyflow/react`, current ~12.10.x)** — the generic, off-the-shelf version of "nodes and animated edges." `BaseEdge` + `getBezierPath`/`getStraightPath` give a custom-edge primitive; `EdgeLabelRenderer` portals HTML labels over the SVG edge layer so a label can carry live text (token count, status) without fighting SVG text layout; and the current API is current and well-documented (Context7, 2026-10-08). **Trade-off vs. TechnoMile's hand-rolled office/pipeline view**: xyflow gives a generic node-graph for free (pan/zoom/drag) but has no built-in concept of "this edge represents a specific recorded latency window" — that semantic binding (the actual thing that makes TechnoMile's office feel truthful rather than decorative) would have to be built on top, the same work already done once for the office/pipeline views. xyflow is a stronger fit if the arena ever wants a literal agent-to-agent message graph (TechnoMile's own `swarm-graph.tsx` is this, already built, and I7 flagged it "optional, lower priority than the office scheduler").
- **Streaming text / token-reveal**: 2026 convention (per the shimmer/skeleton research below) is cross-fade, not instant swap — placeholder shimmer bars fade out while real text fades in word-by-word with a small stagger, so arrival reads as intentional rather than a jump-cut. Several current component libraries (shadcn-derived, Nuxt UI's `ChatShimmer`) ship this as a named, reusable primitive specifically for AI-chat-style streaming.
- **Shimmer/skeleton**: a moving-gradient shimmer over a content-shaped placeholder is now the explicit convention Linear/Vercel/Stripe are all cited as using, with the design rule "reserve the space the real content will take" (no layout shift) — matches TechnoMile's own "no layout shift" rule (section 3) exactly.
- **Timeline scrubbing/replay**: 2026 implementations (Steel's "Agent Traces," a Slicer workflow-replay widget) converge on the same shape TechnoMile already built independently: a draggable playhead scrubber with per-event color-coded ticks, step markers (queued/running/done), and a detail panel for whatever the playhead is over. TechnoMile's own replay (8x speed, 6s cap on quiet stretches, frozen character loops on pause) is at least as sophisticated as the external examples found — this is confirmation, not a gap.
- **Progressive disclosure for multi-agent work, generally**: 2026 guidance converges on "stream the agents' reasoning as it develops rather than only the final verdict" and "every element either supports the current decision or gets removed — secondary data lives behind a deliberate interaction." TechnoMile's pipeline view (rail = secondary/always-visible, canvas = primary/one-at-a-time) is a direct, already-built implementation of this rule.

**Trade-off to flag explicitly (carried from X5's own contradiction-tracking):** AI Digest's "AI Village" (cited in X5) deliberately shows *full* chain-of-thought for every agent, always, as entertainment/transparency theater; this product's own candidate pipeline view defaults to *one step's detail at a time*. Both are legitimate; the arena's "agents visibly doing work" requirement is satisfiable by either a full-transparency mode or TechnoMile's progressive-disclosure default — likely a mode toggle (as X5 already concluded), not a single answer, and not this route's call to make.

## 3. Motion design principles for calm, premium product UI

**Tokens (external 2026 convention, for comparison against TechnoMile's own working token set):**

| | External 2026 convention (cited range) | TechnoMile's actual tokens (`docs/design/motion.md`, in production) |
|---|---|---|
| Duration scale | 4-6 named values typical: instant ~50ms, fast ~100ms, normal ~200ms, moderate ~300ms, slow ~400ms, deliberate ~600ms | `--duration-instant` 90ms (hover/press), `--duration-fast` 150ms (disclosure), `--duration-base` 220ms (entrances), `--duration-slow` 360ms (stage-strip fill), `--duration-data` 600ms (meters/bars arriving) |
| Easing | Entrances: bold curve, long enough to track (~250ms); exits: shorter, faster, less dramatic (-50 to -100ms vs. entrance) | `--ease-out-quart` (state changes), `--ease-out-expo` (entrances/data arrival), `--ease-in-out-quart` (the running-stage sweep) — three curves, each with one assigned job, not a general-purpose "ease" |
| Spring presets | Named families: gentle / smooth / bouncy / snappy / elastic | Not used — TechnoMile uses no spring model at all, pure keyframe/transition CSS |
| Stagger | 40-80ms between list items is "fast enough to feel fluid, slow enough to perceive individually"; decelerating stagger (short-then-long delay) reads as "settling" vs. uniform stagger reading as mechanical | `--stagger-step` 35ms per item, capped by the caller — at the aggressive end of the external range, consistent with "calm but not slow" |

**Choreography and interruption handling (external guidance, option set):** the three named choreography patterns are **stagger** (same motion, offset start — a list), **cascade** (elements in dependency order — step 2's entrance waits for step 1's exit), and **shared motion** (conceptually linked elements moving in lockstep — e.g. an evidence chip and its matrix cell). For interruption: design animations to be interruptible by new user input mid-transition (don't lock input during a 220-360ms entrance); for any sequence over ~500ms, offer a skip; and `prefers-reduced-motion` should collapse a *sequence* to an instant state change, not just play it faster. TechnoMile's own doctrine (below) satisfies all three without naming them explicitly: "one meaning per animation," "only `transform`/`opacity`," "store updates batched ~10Hz so a burst of events plays once per batch, not once per event" (this *is* interruption handling — a flood of fast-arriving events never queues up a backlog of individual animations), and the full reduced-motion collapse-to-1ms rule.

**Measuring 60fps on low-end hardware (this is the one area where the external research adds a concrete new tool over what TechnoMile already measured):**

- **TechnoMile's own method** (already proven, `motion.md`'s verification log): capture frames during a live streaming session and during an accelerated replay, report frame count over a fixed window, p50/p95 frame time, and count of frames exceeding 50ms, plus Cumulative Layout Shift. This is the right methodology and should be re-run, unchanged, against the arena's own live-trial view before claiming 60fps for it (I7 already recommended this; this route confirms there's nothing newer that should replace it).
- **New tool to add to that method**: the **Long Animation Frames (LoAF) API** (`PerformanceObserver` with `{type: 'long-animation-frame', buffered: true}`) is the current browser-standard way to get the *same* "which frame missed its budget, and by how much, and why" data programmatically, with `blockingDuration` breaking out how much of the overrun was actually un-yielding JS vs. render work. It supersedes the older Long Tasks API specifically for animation diagnosis. **Trade-off**: TechnoMile's manual capture-and-report method is already proven and gives exact numbers for a sign-off doc; LoAF is better for *continuous* in-the-field monitoring (it could feed a real telemetry pipeline) but adds a new instrumentation surface this project would have to build and would need its own default-deny/redaction treatment consistent with section 10 of `02-direction.md` if it ever reports timing data anywhere traced.
- **Low-end-hardware simulation**: Chrome DevTools' Performance panel CPU-throttling control (the gear icon, "6x slowdown" preset being the commonly cited stand-in for a low-end laptop) is the standard way to pressure-test the 16.7ms/frame budget before trusting a measurement taken on a developer's own fast machine. The research explicitly flags that **mean frame time is a weak signal** — a trace can average under-budget while still containing visible stutter — which is exactly why TechnoMile reports p95 and a "frames over 50ms" count rather than an average; that choice is confirmed as the right one, not just a TechnoMile idiosyncrasy.

**Trade-off for the owner's "amazing, stunning" mandate vs. this project's actual constraints:** PRB-4 (avatar demeanor/voice independent of role; nervousness is never evidence) and the assessment-mode coaching gate (coaching must be fully hidden, not just visually de-emphasized, during assessment) both mean some of the most "impressive-looking" motion ideas — a visibly anxious-looking subject avatar, a coaching panel that fades to translucent instead of disappearing — are the exact things the product rules forbid. The safest reading of "amazing and stunning" that survives every constraint already locked in `02-direction.md` is TechnoMile's own model: motion that is *extremely well-executed and perfectly smooth* in service of *state the user is allowed to see*, not motion that adds new meaning the protocol doesn't already produce. That is an option to weigh, not a decision made here.

## 4. UX writing with no AI jargon

**General guidance found (2026, converging across multiple style-guide sources):** avoid naming the AI in the feature name at all where possible ("most features shouldn't have 'AI' in the name — it waters down the feature, and as AI becomes ubiquitous, naming it will look dated"); write in plain, concrete, everyday words over technical/corporate jargon; avoid the generic "AI-sounding" filler vocabulary itself (delve, cutting-edge, multifaceted, leverage, robust, facilitate, optimize, "in summary," "it's important to note," and formal transition words like "furthermore/moreover/consequently" in favor of "also/but/so/because of this"). The common thread across every source: **jargon raises cognitive load for the reader** — pick the word a first-time user already knows, not the word that is technically most precise.

**Word substitutions for this product's actual screens** (synthesized from the general guidance above, applied against this product's own vocabulary in `02-direction.md`/REQUIREMENTS — **not independently sourced per substitution, flag accordingly**):

| Internal/engineering term | What it names (from `02-direction.md`) | User-facing substitute | Why |
|---|---|---|---|
| "AI assistant" / "assistant candidate" / "agent" | A coaching model giving the investigator a complete card (question-type read, flags, follow-up, finding+confidence) each turn | **"coach"** | Names the role (what it does for the trainee), not the technology; matches the Disco-Elysium-style "inner voice" framing X5 already recommended, and avoids implying the coach has independent judgment it must not have under PRB-4 |
| "Inference" / "model call" / "the model generated..." | A single structured call to Gemini on Vertex | **"check"** (e.g. "running a check," "check complete") | Describes the *action from the trainee's point of view* (something was checked), not the mechanism; also sidesteps naming which model/vendor ran it, consistent with not needing to disclose implementation detail to a trainee |
| "Subject" (as UI-facing noun) | The role-played interviewee | **keep "subject"** in investigator-facing UI — it is already the domain's own term of art (interrogation training), not AI jargon; do not relabel to something softer, since EX-4's synthetic-only ground rule needs this role named plainly, not euphemized |
| "Finding: deceptive / truthful / insufficient evidence" | The coach's running classification, with ICD 203 confidence wording | **keep the three states as written**, but the *confidence* language (ICD 203 wording like "likely," "roughly even odds") should stay in its own already-specified vocabulary — this is intelligence-community language the sponsor (Unissant, serving ICE/CBP/DHS/etc.) already expects, not AI jargon to be removed |
| "Latency" / "p95 coaching latency" | KPI-4, the 3-second coaching budget | **"how fast the coach responds"** in any trainee-facing copy; keep "latency"/"p95" in judge-facing/ops surfaces (Phoenix, methodology page) where the audience is technical | Audience-dependent: a trainee never needs the metric's name, a judge evaluating KPI-4 does |
| "Hallucination" / "unsupported flag" | A flag whose cited span doesn't support the claim | **"flag without a matching quote"** or "flag needs a source" | Plain description of the actual failure mode beats the industry jargon term, and is more actionable for a trainee learning to self-check their own flags |
| "Tournament" / "candidate" / "manifest" | Bake-off internals (`arena.tournaments`, `arena.candidates`) | **keep entirely out of any trainee-facing screen** — these are ops/judge vocabulary (leaderboard, methodology page) and should never leak into the training room | Jargon that's fine for judges reading the methodology page is still jargon for a trainee in the interrogation room |
| "Synthetic-only ground rule" (EX-4) | The disclosure that cases/scores are not about a real person | Plain sentence, sponsor's own wording already drafted in X5's open question: **"This is a training simulation. All cases are made up — a simulated score is not a finding about a real person."** | X5 already flagged that no canonical UI convention for this disclaimer was found; this route does not re-solve that open design problem, it only confirms the plain-language direction is correct and gives a draft sentence to start from |

**Trade-off:** "no AI jargon" and "assessment mode hides coaching" pull toward the same place — the less the UI talks about *how* the coach works, the easier it is to make the coaching panel disappear cleanly in assessment mode rather than being "faded AI content" that a trainee can tell used to be there. Treating word choice and the assessment-mode hide as one design problem (not two) is a cheap way to satisfy both EX-4/assessment-mode and "no jargon" at once.

## 5. Contradictions / open tensions (not resolved here)

1. **"Amazing, stunning" vs. the industry's own most-copied references being deliberately quiet.** Linear's own motion is characterized as mostly 80-120ms linear transitions with explicitly "no decoration-animations." TechnoMile's doctrine is the same philosophy taken further (zero library, one meaning per animation). The owner's mandate for "amazing and stunning" and the pattern most design-literate teams actually ship are in tension; "amazing" likely has to come from *polish and correctness* (buttery frame pacing, zero jank, perfect reduced-motion fallback) rather than *more motion*, if it is to coexist with PRB-4/EX-4/assessment-mode. Flagged for the owner's DESIGN.md, not resolved here.
2. **Full-transparency "agents at work" (AI Village) vs. progressive-disclosure pipeline view (TechnoMile).** Already flagged in X5; this route confirms TechnoMile has since *built* the progressive-disclosure answer as a real, shipped pipeline-view spec, strengthening that side of the tension without closing it — a toggle between both modes remains the likely answer.

4. **Theatre.js's current maintenance health could not be confirmed from a primary source this route** — only third-party skill/doc mirrors surfaced. Treat as the weakest-evidence entry in section 1's table; do not commit build time to it without checking the actual GitHub repo's commit history first.
